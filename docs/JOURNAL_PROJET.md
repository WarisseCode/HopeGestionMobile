### T-005 : Exclusion CORS + garde `Origin` sur `/api/auth/mobile/*`
- **Date** : 2026-09-18
- **Statut** : Terminée (vérification manuelle par curl bloquée, voir ci-dessous)
- **Type** : Fonctionnalité / Config
- **Description** : Les requêtes vers `/api/auth/mobile/*` ne passent plus par le middleware `cors` global et sont rejetées en 403 si elles portent un en-tête `Origin` (quelle que soit sa valeur), afin qu'un script de page web (y compris via XSS) ne puisse jamais atteindre ces routes, même en cross-origin autorisé.
- **Fichiers touchés** : `HopeGestionV2/backend/index.ts`.
- **Décisions & justifications** : détection de chemin par regex insensible à la casse (`/^\/api\/auth\/mobile(\/|$)/i`), car le routage Express ne l'est pas par défaut et rien dans le projet n'active `case sensitive routing`/`strict routing`. Options CORS existantes extraites à l'identique dans `corsMiddleware`, aucune régression sur les autres routes.
- **Problèmes rencontrés** : la vérification manuelle par curl (4 scénarios attendus) n'a pas pu être exécutée — aucune instance PostgreSQL locale n'est joignable dans cet environnement (`DB_HOST=localhost`, timeout de connexion), ce qui empêche `index.ts` de démarrer. `npm test` et `tsc --noEmit` restent verts. À refaire dès qu'une base locale est disponible.

### T-011 : Audit sécurité multi-tenant RLS — backend HopeGestionV2 (lecture seule)
- **Date** : 2026-09-21
- **Statut** : Terminée
- **Type** : Documentation
- **Description** : Audit en lecture seule de l'isolation multi-tenant (Row-Level Security PostgreSQL) sur les 12 tables listées par l'utilisateur, en complément du contexte prod fourni (6 tables `FORCE` RLS, 6 non forcées). Analyse de `middleware/tenantGuard.ts`, du texte des policies (`db-local/schema.sql`), et recherche exhaustive des appels `pool.query()` bruts vs `req.dbClient.query()` sur ces 12 tables (routes, services, crons, webhooks), via un agent Explore dédié pour l'énumération mécanique puis vérification manuelle de chaque site à risque.
- **Fichiers touchés** : aucun côté code (audit) ; ce fichier journal uniquement.
- **Décisions & justifications** : rapport structuré en 6 points selon la demande (tenantGuard, policies, tables non forcées, contexte périmé, routes sans tenantGuard, correctifs proposés non appliqués), chaque finding classé par sévérité avec fichier:ligne à l'appui.
- **Problèmes rencontrés** : deux fuites cross-tenant **critiques et confirmées par lecture directe du code** (pas seulement théoriques) : `GET /api/mobile-money/transactions` (`routes/mobileMoneyRoutes.ts:96-105`) et `GET /api/tickets` (`routes/ticketRoutes.ts:47-89`) — toutes deux correctement branchées sur `req.dbClient` (donc pas un problème de contexte périmé) mais sans aucun filtre `owner_id` applicatif, alors que `mobile_money_transactions` et `tickets` ne sont pas sous `FORCE ROW LEVEL SECURITY` : n'importe quel utilisateur authentifié voit les données de tous les tenants sur ces deux endpoints. Un troisième défaut, distinct (IDOR, pas RLS) : `GET /api/compte/proprietaires/:id/biens` (`routes/compteRoutes.ts:575-611`) et `GET /api/owners/:id/properties` (`routes/ownerRoutes.ts`) n'utilisent que le rôle applicatif de l'appelant pour autoriser l'accès, sans jamais vérifier que l'`:id` demandé lui appartient — accès complet aux biens de n'importe quel propriétaire en changeant l'ID dans l'URL. Par ailleurs, l'historique git montre que tout le dispositif RLS (fonctions `get_current_*_id`, `ENABLE`, et en particulier `FORCE`) n'a jamais été capturé dans une migration versionnée : le seul fichier qui l'a documenté (`backend/db/migration_rls.sql`, avril 2026) a été supprimé en juin 2026 sans jamais contenir de `FORCE`, confirmant que le `FORCE` actuellement actif en prod sur 6 tables a été appliqué manuellement, hors contrôle de version — aucun correctif RLS n'est donc testable ailleurs qu'en prod tant que cet état n'est pas reconstitué dans une migration.

(4) Nouvelle classe `ApiException` (`lib/core/network/api_exception.dart`, type/statusCode/message/fieldErrors), levée par la nouvelle méthode `ApiClient.request<T>()` qui enveloppe `dio` et traduit toute `DioException` — `dio` reste accessible directement pour les usages bas niveau et les tests d'intercepteur. (5) Timeouts (connect 15 s, send/receive 30 s) ajoutés aux `BaseOptions` par défaut des deux clients Dio ; `LogInterceptor` ajouté en debug uniquement, sans en-têtes ni corps, positionné après l'intercepteur d'auth pour ne logger que le résultat final. Deux améliorations demandées : (6) une requête dont le 401 revient alors que le cache contient déjà un token différent de celui envoyé (un refresh concurrent a fini entre-temps) est rejouée directement avec le token courant, sans déclencher de nouveau refresh ; (7) le rejeu d'une requête `FormData` utilise `FormData.clone()` (vérifié présent dans dio 5.11.1), sans quoi le rejeu d'un upload échouerait (`FormData` déjà `finalize()`, non réutilisable).

- **Décisions & justifications** :
  - Distinction à trois voies de l'échec de refresh (`_RefreshFailureKind` : `deauth` / `transient` / `aborted`), calculée une seule fois dans `_performRefresh` (donc partagée par tous les 401 concurrents via le même `_refreshFuture`) plutôt que recalculée dans chaque appel à `_onError` : évite qu'un événement `sessionExpired` soit émis plusieurs fois pour un seul refresh refusé — testé explicitement avec 3 requêtes 401 concurrentes.
  - Sur un échec `transient`, l'erreur remontée à l'appelant porte les `requestOptions` de la requête D'ORIGINE mais le `type`/`response` du refresh (`_transientRefreshError`) : ni un nouveau `DioException` générique, ni le 401 d'origine (qui classerait à tort en `unauthorized`) — c'est ce qui permet à `ApiException.fromDioException` de retrouver la vraie cause (`network`/`timeout`/`rateLimited`/`server`).
  - `_isMobileAuthRoute` (`/auth/mobile/*`, pour l'en-tête `Authorization`) est volontairement plus étroit que `_isAuthRoute` (`/auth/*`, pour le blocage du refresh) : `PATCH /auth/complete-profile` (protégée par un vrai token depuis le correctif lot 1b, backend `HopeGestionV2`) a légitimement besoin de son `Authorization`, contrairement à `/auth/mobile/login|refresh|logout`. Un 401 sur `complete-profile` ne déclenche pas non plus de refresh (demande explicite), différence assumée et documentée en commentaire — pas une omission.
  - `request<T>()` (méthode qui enveloppe `dio` et convertit en `ApiException`) plutôt qu'un intercepteur terminal supplémentaire : un intercepteur ne peut compléter/rejeter qu'avec une `DioException` (jamais un type arbitraire), donc convertir au niveau de l'intercepteur aurait de toute façon nécessité un déballage manuel côté appelant (`err.error as ApiException`) — la traduction au point d'appel est le pattern Dio standard, plus simple à lire, et garde `dio` disponible tel quel pour les tests bas niveau de l'intercepteur (déjà écrits en T-018, conservés inchangés).
  - Timeouts choisis pour un réseau mobile 2G/3G intermittent (contexte Bénin, cité par l'utilisateur) : 15 s en connexion (assez court pour ne pas bloquer l'UI sur une absence totale de réseau), 30 s en envoi/réception (assez long pour un upload/téléchargement de document sur une connexion lente sans déclencher de faux timeout). Valeurs par défaut uniquement : ignorées si l'appelant fournit ses propres instances `Dio`/`refreshDio` (cas de tous les tests).
  - `LogInterceptor` ajouté APRÈS l'intercepteur d'auth (vérifié dans le code source de `dio` : les intercepteurs sont parcourus dans le même ordre pour `onRequest`/`onResponse`/`onError`) pour qu'il ne voie que le résultat final (après un éventuel refresh+rejeu), jamais le 401 intermédiaire — et avec les 4 flags d'en-têtes/corps désactivés, conformément à « jamais de token ni de corps dans les logs ».
  - Contrat exact de `FormData.clone()` vérifié dans le code source de dio 5.11.1 installé (pas de mémoire) avant de l'utiliser.
- **Problèmes rencontrés** : un test (`401 concurrents avec émission unique de sessionExpired`) a d'abord échoué avec `Future.catchError` (« must return a value of the future's type ») — un `catchError` ne peut pas renvoyer l'exception elle-même quand elle n'est pas du même type que la valeur de succès (`Response<T>` vs `ApiException`) ; corrigé avec un petit helper `_captureError` (try/catch explicite renvoyant `Object?`).
